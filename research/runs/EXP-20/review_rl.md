# EXP-20 PowerSGD — RL / GRPO-objective review (`rl-grpo-checker`)

- **Branch / commit reviewed:** `origin/exp/20-powersgd-activation` @ `f748dbc1c63ef9824a3115b091ed025fe210cf9b`
- **Lens:** does the boundary activation compression preserve a *valid vanilla-GRPO update*? (orthogonal to the pure-math and numerics lenses)
- **Sources:** issue #20 (Parts II, V.3, VII.4, INF-9, INF-17, INF-19), plan `.claude/plans/20.md`, committed code.
- **Bottom line:** **VALID with two CAVEATs.** The GRPO objective itself is untouched (diff confined to the comm_eff codec; no-KL/no-entropy/vanilla-clip/grpo-advantage all hold), the frozen-Q ρ≈1 mechanism is correctly implemented, and advantages are provably independent of compression. The two caveats are (a) a **launcher/plan default mismatch on `sync_basis`** that changes *what* GRPO update is computed under DP, and (b) the **train(compressed)-vs-rollout(dense) representation gap** (INF-19) is real and ρ≈1 does **not** diagnose it — it is the live scientific risk the experiment must measure, not a code bug.

## Check 1 — Frozen-Q ⇒ ρ≈1 (INF-17): VALID

**Claim.** With `compress_recompute=true`, the old-logprob recompute runs the SAME compressed forward with the SAME frozen `Q_t` as the actor-train forward, so at step 0 (no weight change) `ρ = exp(logπ_new − logπ_old) = 1`; `Q` advances to `Q_{t+1}` only AFTER the train step.

**Verified — the ratio is between two consistently-compressed forwards, and that is GRPO-correct.**

1. **The ratio denominator IS the (compressed) recompute, not the rollout.** `old_log_probs` is produced by `actor_rollout_wg.compute_log_prob` (`verl/trainer/ppo/ray_trainer.py:1265-1294`, `_compute_old_log_prob`), not by the vLLM rollout. The launcher sets `algorithm.rollout_correction.rollout_is=null / rollout_rs=null / bypass_mode=false` (launcher:374-376), so no rollout-logprob IS correction reinjects the dense rollout logprob into the ratio. The vanilla GRPO ratio is `ratio = exp(log_prob − old_log_prob)` (`core_algos.py:1247-1250`), where `log_prob` = actor-train forward, `old_log_prob` = the recompute.

2. **Both forwards are projected through the same `Q_t`.** The recompute path (`compute_log_prob`, `engine_workers.py:688-708`) stamps `mask_active=True` on `path_tag="old_logprob"` *iff* `powersgd is not None and compress_recompute and not clean_step`. The train path (`update_actor`, `engine_workers.py:916-919`) stamps `mask_active = not clean_step` on `path_tag="train"`. The gate `_comm_eff_powersgd_active` (`transformer_impl.py:733-764`) admits the hook on `train`⇒`not forward_only` and `old_logprob`⇒`forward_only`. Both forwards therefore install the identical projection hook reading the identical per-layer `Q_t` from `self._basis[layer_idx]`.

3. **`Q` is frozen across the pair and only advances after the gradient-bearing work.** `maybe_update_basis` is called in the `finally` of `update_actor` (`engine_workers.py:941-943`), i.e. *after* `train_mini_batch` (all PPO inner-epoch forwards/backwards) has run. The recompute's `_should_accumulate_sketch` returns False because the recompute runs `forward_only=True` ⇒ whole forward under `torch.no_grad()` (`transformer_impl.py:864`), and the sketch gate requires `grad_enabled` captured at hook entry (`powersgd_activation.py:_make_hook`, the `grad_enabled = torch.is_grad_enabled()` line + `_should_accumulate_sketch(grad_enabled=...)`). So the recompute folds nothing into `V`, and `Q` is identical for both forwards of the step. The update sets `Q_t → Q_{t+1}` for the *next* step (Part V.3 satisfied exactly).

4. **Is the ratio between two consistently-compressed forwards GRPO-correct?** Yes. GRPO's importance ratio is only meaningful as `π_θ_new / π_θ_old` *under the same computational map*. Freezing `Q` makes the compression operator a fixed (step-constant) deterministic function `f_Q(·)` applied identically to both numerator and denominator policies. The ratio then reflects ONLY the weight delta produced by the inner PPO epochs — exactly as dense GRPO. At inner-epoch 0 with no weight change, `log_prob == old_log_prob` bit-for-bit (same weights, same `f_Q`, same inputs) ⇒ `negative_approx_kl = 0` ⇒ `ratio = 1`. INF-17's mechanism is implemented faithfully.

**What would refute me.** A logged step-0 / inner-epoch-0 `ppo_kl` or `pg_clipfrac` that is materially non-zero on the PowerSGD arm with `compress_recompute=true` would mean the two forwards saw different operators (a Q-freeze leak, or sketch accumulation on the recompute). The probe's frozen-Q hard invariant (`plan §Correctness invariants`, ρ≈1) tests exactly this; I confirm the *code path* makes ρ≈1 the expected result.

**Subtlety (not a defect).** With the **default `compress_recompute=true`** the ratio is "compressed/compressed". With `compress_recompute=false` the recompute is **dense** and the train forward is **compressed**, so even at step 0 with no weight change `log_prob ≠ old_log_prob` (different operators) ⇒ ρ ≠ 1 *by construction*. That is intended (the plan lists `compress_recompute true→false` as a REVISE knob that "dense-anchors the old-logprob"), but the analyst must NOT read a ρ≠1 on a `compress_recompute=false` run as a frozen-Q bug — it is the operator mismatch the knob deliberately introduces. The plan's ρ≈1 invariant is scoped to `compress_recompute=true`, which is correct.

## Check 2 — Clean-cadence: VALID (objective + advantage independence), with one optimizer-momentum nuance

**Claim.** On clean steps BOTH forwards are dense ⇒ ρ on dense forwards, AdamW refreshed on the true gradient. Confirm mixing compressed/clean steps does not bias the GRPO objective or corrupt optimizer momentum, and that advantages/returns are independent of compression.

**Verified.**

1. **Clean steps are fully dense on both forwards.** `is_clean_step` = `clean_cadence>0 and gs>0 and gs%cadence==0` (`state.py:431-453`). On a clean step: `update_actor` sets `mask_active=False` (`engine_workers.py:917`, `not clean_step`); `compute_log_prob` suppresses the recompute stamp (`engine_workers.py:700`, the `not clean_step` guard). Both `_comm_eff_powersgd_active` calls then return False (`mask_active` False), so NO projection hook registers ⇒ both forwards are byte-identical dense. ρ on a clean step is a genuine dense GRPO ratio, and AdamW's `.step()` runs on the true full-rank gradient. `maybe_update_basis(is_clean_step=True)` early-returns without touching `Q` (`powersgd_activation.py`, the `if is_clean_step:` branch), and `clean_steps += 1` (`engine_workers.py:925`). This mirrors the exercised PRF clean-step path exactly.

2. **Does mixing compressed/clean steps bias the GRPO objective?** Per-step, no — each step optimizes a *self-consistent* GRPO objective (numerator and denominator share the step's operator, compressed or dense). The compressed steps optimize a **projected** policy gradient (`dL/dM = (dL/dM_hat)·QQᵀ`, the self-adjoint projector, INF-9) — a *biased-but-consistent* estimate confined to the rank-r hidden subspace; the clean steps inject the unbiased full-rank gradient. This is exactly the INF-10 design: clean cadence is a **strictly weaker debiaser than error feedback** (it gives intermittent unbiased gradients, not the telescoping `Σ sent = t·G − e` guarantee, because the dropped residual `M − M_hat` is discarded, Part II). So "unbiased over the whole trajectory" is **not** guaranteed by the math — it is the empirical hypothesis the 50-step curve-match tests. The code implements the intended (weaker) debiaser correctly; the residual bias is a *scientific* risk owned by the analyst's verdict, not a code defect.

3. **Optimizer-momentum nuance (CAVEAT, low severity).** AdamW's first/second moments are stateful across steps. On compressed steps the gradient fed to AdamW is the subspace-projected gradient; on clean steps it is full-rank. So the optimizer's running moments are an EMA over a *mixture* of projected and full-rank gradients — the clean step does not "reset" momentum, it just contributes one unbiased sample to the buffers that otherwise accumulate biased (projected) samples. This is **identical in kind to the PRF-mask + clean-cadence baseline** (the byte-matched bar also feeds masked-then-clean gradients into the same AdamW), so it is **not a confound between the two arms** — both arms share the momentum-mixing behavior, and the comparison is apples-to-apples. It is worth stating only because "AdamW refreshed on the true gradient" (the task's phrasing) slightly overstates it: the clean step refreshes momentum *toward* the true gradient by one EMA step; it does not give a from-scratch true-gradient optimizer state. No action needed for the matched comparison.

4. **Advantages/returns are independent of compression — CONFIRMED.** The diff touches NO file in the advantage/reward/return path: `git diff --name-only origin/vast-ai-workload...exp/20` returns nothing matching `core_algos|advantage|reward|ray_trainer|dp_actor|compute_advantage|ppo`. GRPO advantages are the group-normalized rewards over the `n=8` rollouts per prompt (`adv_estimator=grpo`, `run_qwen3_4b_fsdp.sh:61`), computed from **uncompressed vLLM rollouts** (rollout is `path_tag="rollout"`, never compressed — the gate only admits `train`/`old_logprob`). Rewards come from the GSM8K verifier on rollout text. Compression enters ONLY the policy-gradient via `M_hat` on the train (and optionally old-logprob) forward — never the reward or the advantage. The advantage signal driving learning is therefore identical to dense GRPO.

**What would refute me.** A nonzero `comm_eff/powersgd_applications/<tag>` for any tag other than `train` (the recompute increments the aggregate but the gate is path-checked), or any advantage/return value differing between the dense-ceiling and PowerSGD arms beyond rollout stochasticity, would indicate compression leaked into the measurement path. The path counters + the confined diff make this checkable and currently clean.

## Check 3 — Vanilla-GRPO invariance (comm_eff OFF ⇒ byte-identical): VALID

**Claim.** comm_eff OFF ⇒ byte-identical dense GRPO; the ONLY change with powersgd is the boundary activation projection; no spurious KL/entropy/clip alteration.

**Verified.**

1. **OFF path is a strict no-op.** `maybe_build_comm_eff_state(config)` returns `None` when `enabled=false` (`state.py:664-677`) — no object, no RNG, no hook. Every comm_eff call site short-circuits on the `None` check (`engine_workers.py:887-943`; `transformer_impl.py:_comm_eff_powersgd_active` returns False on `state is None`). So a dense run draws the same RNG and issues the same collectives as upstream (the parity contract). The `update_actor` metrics block even emits explicit `powersgd_applications/basis_updates = 0` zeros on the disabled path (`engine_workers.py:999-1000`) — a constant metric, not a training side effect.

2. **The ONLY active-path change is the projection.** No KL: launcher pins `use_kl_loss=False` + `use_kl_in_reward=False` (launcher:195-196, 384-385). No entropy: `entropy_coeff=0` (launcher:198, 386). Loss is `loss_mode="vanilla"` (`algorithm.yaml:55-61` default; launcher does not override it) ⇒ `compute_policy_loss_vanilla`, the standard clipped PG with `ratio = exp(log_prob − old_log_prob)` (`core_algos.py:1247+`). The powersgd codec does NOT touch the loss, the clip range, KL, or entropy — it only rewrites the boundary block *output activation* via a forward hook. The clip fraction `pg_clipfrac` is computed from the (compression-consistent) ratio, so a clipfrac dip on clean steps is the dense refresh (expected, plan §Notes for analyst), not a clip alteration.

3. **No-KL/no-entropy holds for the PowerSGD arm too** — these are launcher-level and codec-agnostic; the codec cannot reintroduce them.

**What would refute me.** A nonzero KL-loss term or entropy term in the logged loss decomposition on any EXP-20 arm, or an off-path parity step-1-loss mismatch > 1e-4 rel vs the dense control (the plan's hard "off-path parity" invariant). Both are checked by the probe; the code path supports byte-identity.

## Check 4 — Train(compressed-actor)-vs-inference(uncompressed-vLLM) gap: CAVEAT (real, by design; ρ≈1 does NOT diagnose it)

**Claim to assess.** The policy gradient is computed on PROJECTED activations while rollouts are uncompressed — does this introduce a systematic bias? Is ρ≈1 the right diagnostic, or could it mask a deeper objective mismatch?

**Assessment — this is the load-bearing RL-specific risk, and the task's framing is correct: ρ≈1 is NECESSARY but NOT SUFFICIENT.**

1. **The gap is real and is exactly INF-19.** Per scope (Part VII.4) and the `train`-only (+ optional `old_logprob`) eligibility, rollouts are generated by **dense vLLM** (`path_tag="rollout"`, never compressed). The policy being *trained* sees projected activations `M_hat = M·QQᵀ`; the policy that *generated the data* (and computes advantages) is dense. So there are effectively two policies: `π_gen` (dense) and `π_train` (the projected map `f_Q∘π`). This is the **direct analog of this project's documented masked-actor-vs-vLLM gap** (memory: `exp16-train-inference-gap`).

2. **Why ρ≈1 does NOT cover it.** ρ = exp(logπ_new − logπ_old) compares the two **train-side** forwards. With frozen Q both are `f_Q∘π`, so ρ≈1 says *"the two compressed train forwards agree."* It says **nothing** about whether `f_Q∘π` (trained) matches `π_gen` (dense rollout). The mismatch between the trained representation and the generating representation is a *separate* axis that ρ is structurally blind to — it would read ρ≈1 even if `f_Q∘π` were arbitrarily far from `π_gen`. So ρ≈1 can **mask** the train/inference objective mismatch: it is the correct diagnostic for the frozen-Q invariant (Check 1) but the WRONG diagnostic for the representation gap. The right diagnostics are the ones the plan/issue already name: `powersgd_reconstruction_rel_error` (INF-19: "the gap is bounded by ‖M − M_hat‖"), the **dense-vs-compressed update cosine** (the plan's headline direction-agreement metric), and ultimately the **reward trajectory** vs the byte-matched mask.

3. **Is the bias systematic?** Yes, structurally: every compressed train step confines both the activation and its gradient to the rank-r hidden subspace (INF-9, self-adjoint `QQᵀ`), so the orthogonal-complement directions of the policy gradient are **zeroed every compressed step**. The advantages, however, were computed for the *dense* rollout policy. So the update is "move the *projected* policy in the subspace-confined direction that would have improved the *dense* policy's sampled returns." Whether that is a good ascent direction for the dense policy depends entirely on the spectral precondition (INF-20: are these activations effectively low-rank?) and is **modulated by the clean steps** (which re-admit the full-rank direction every K) and by `compress_recompute` (true keeps the IS ratio self-consistent; false dense-anchors the denominator). This is precisely the hypothesis under test — the code does not (and cannot) eliminate the bias; it provides the two levers (clean cadence, compress_recompute) the experiment sweeps.

4. **Same-family as PRF, so the comparison is fair.** The byte-matched PRF-mask baseline has the *identical* train/inference gap (masked train forward, dense rollout). So this gap is **not** a confound that advantages PowerSGD or the mask — both arms carry it. The experiment asks the right question: *at equal budget + equal clean cadence, does the low-rank projection track the random mask?* The gap is the backdrop for both, not a differentiator.

**CAVEAT (medium severity, scientific not code).** The verdict logic must treat ρ≈1 (frozen-Q invariant) and the reward/cosine/reconstruction metrics (representation-gap health) as **independent gates**. A PASS on ρ≈1 plus a degrading reward trajectory is NOT a contradiction — it is exactly the signature of "frozen-Q is implemented correctly, but the projected policy gradient is a poor ascent direction for the dense rollout policy" (the INF-19/INF-20 failure mode). The plan's success criteria already separate these (frozen-Q is a probe gate; reward@50 / cosine / reconstruction are the headline), so the **plan is structured correctly**; I am flagging it so the analyst does not over-credit a clean ρ≈1.

**What would refute me.** If a logged metric showed the trained-policy logprobs converging to the dense-rollout logprobs *independently of* reconstruction error (e.g. reward tracking dense while reconstruction_rel_error stays high), that would mean the gap is not reconstruction-bounded as INF-19 claims and my "ρ≈1 is insufficient" caution would be over-stated. The dense-vs-compressed update cosine is the cleanest single number that would confirm or refute the direction-agreement concern.

## Cross-lens overlaps (CONFIRM / CHALLENGE)

- **Frozen-Q (shared with math claim 4): CONFIRM.** The freeze is enforced by *ordering* (`maybe_update_basis` in `update_actor`'s `finally`, after `train_mini_batch`) AND by *path gating* (the recompute is `no_grad` ⇒ no sketch). Both must hold; both do. I add the RL-specific consequence the math lens may not state: the freeze is what makes the GRPO IS ratio a pure weight-delta ratio (Check 1), which is the *reason* the freeze is GRPO-required, not just a determinism nicety.

- **`sync_basis` default (shared with the distributed lens): CHALLENGE / escalate.** **CAVEAT, high severity for reproducibility of the recorded result.** The dataclass default and the issue/plan VII.1 config both say `sync_basis=false` (plan §Experiment sequence step 2: `powersgd.sync_basis=false`; issue VII.1: `sync_basis: false`). But the **launcher overrides it to `true`** (launcher:280, `COMM_EFF_POWERSGD_SYNC_BASIS="${...:-true}"`, annotated "REQUIRED under DP"). The RL stakes: with `sync_basis=false` under DP=4, each rank orthonormalizes its OWN shard's `V`, so the four ranks hold **four different codebooks `Q`**. Under FSDP the four ranks then compute a *single averaged gradient* over four *different* projection operators — i.e. the effective forward map is not a single well-defined `f_Q`, and `M_hat` differs per rank for the same token. That is not a valid single-policy GRPO forward; the recompute and train forward on a given rank still share that rank's Q (so per-rank ρ≈1 may still hold), but the **all-reduced gradient mixes operators**, and the cross-rank Q-agreement invariant (hard-invariant #4) would FAIL. The launcher default `sync_basis=true` is the **RL-correct** choice — it all-reduces the raw `V` before `orth`, giving a bit-identical consensus `Q` on every rank (`maybe_update_basis` consensus path + `verify_basis_agreement_across_ranks`, which RAISES on divergence). **The code is correct; the hazard is the plan/issue text vs the launcher default disagreeing.** Recommendation: the runner must launch step 2 with `sync_basis=true` (the launcher default already does this) and must NOT "fix" it back to the plan's `false` — and the analyst should confirm `comm_eff/powersgd_q_cross_rank_max_rel_dev == 0.0` is logged. If anyone runs with `sync_basis=false` on >1 GPU, the run trains divergent codebooks and the result is not a valid GRPO update. (Flagged to the distributed-lens reviewer; this is where my RL lens and theirs intersect.)

- **Gradient behavior (shared with numerics lens): CONFIRM.** The backward is the exact self-adjoint projector (no STE), so the *policy gradient* — not just the activation — is subspace-confined every compressed step (INF-9). The RL consequence (Check 4) is that this confined gradient is applied against advantages computed for the unconfined dense rollout policy. The numerics lens owns "is the gradient finite / well-scaled"; I own "is the confined gradient a valid GRPO ascent direction" — answer: consistent per-step, biased over the trajectory, debiased only intermittently by clean steps (INF-10). No STE means no gradient-estimator mismatch of the kind that plagued earlier no-rescale masking (memory `exp16-norescale-gradnorm`); the projector is norm-non-expansive (`‖M_hat‖ ≤ ‖M‖`, INF-2), so it cannot *inflate* the gradient the way constant-rescale masking did.

## Bottom line

From the **GRPO/RL objective** lens the implementation is **VALID**:
- the GRPO objective (vanilla clipped PG, group-normalized advantages, no-KL, no-entropy) is provably untouched — the diff is confined to the comm_eff codec, and advantages/rewards derive entirely from uncompressed vLLM rollouts;
- the frozen-Q ρ≈1 mechanism (INF-17) is implemented correctly via both forward-ordering and path-gating, making the GRPO importance ratio a pure weight-delta ratio;
- clean steps are genuinely dense on both forwards and feed the true gradient into the (shared-with-baseline) optimizer state;
- comm_eff OFF is a strict byte-identical no-op.

**Two things must be carried into the run/verdict, not the code:** (1) **launch step 2 with `sync_basis=true`** (launcher default; the plan/issue text saying `false` is unsafe under DP and would train divergent codebooks — escalate to the distributed reviewer / operator); and (2) **ρ≈1 is necessary but not sufficient** — the train(compressed)-vs-rollout(dense) representation gap (INF-19) is the real scientific risk and is diagnosed by reward-trajectory + update-cosine + reconstruction-error, which the plan already separates from the frozen-Q probe gate. No RL-correctness change to the code is required.
