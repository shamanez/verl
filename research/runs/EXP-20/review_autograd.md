## Check 1 — `M_hat=(M@Q)@Qᵀ`: Q detached, M in-graph, self-adjoint backward, NO STE — **VALID**

Hook body (`powersgd_activation.py:332-340`):
```python
M = h.reshape(-1, hidden_size)
q_fp32 = compressor._ensure_basis(layer_idx, device=M.device, dtype=M.dtype)
q_act  = q_fp32.to(dtype=M.dtype)
Y      = M @ q_act          # (N, r)
M_hat  = Y @ q_act.t()      # (N, H) — in-graph through M
```
- **Q is a non-leaf constant, no graph edge.** `self._basis[layer_idx]` is produced by `init_basis`→`orthonormalize`, both of which start from `mat.detach().to(torch.float32)` / a fresh `torch.randn` and run `torch.linalg.qr` (`:102-152`). It is stored in a plain dict — never an `nn.Parameter`, never a registered buffer, never `.requires_grad_(True)`. `q_act = q_fp32.to(dtype=M.dtype)` is a dtype cast of a `requires_grad=False` tensor ⇒ still `requires_grad=False`. So `dM_hat/dQ` is never formed; Q contributes no edge.
- **M stays in-graph.** `M` is a `reshape` view of the live block output `h`; both matmuls are ordinary differentiable ops. The returned `M_hat.reshape(orig_shape)` feeds the next block, so the loss graph runs `… → h → M → Y → M_hat → next block → loss`.
- **The backward torch *computes* is the self-adjoint projector — by autograd, not by construction.** With Q constant, `M_hat = M(QQᵀ)`, so `dL/dM = (dL/dM_hat)(QQᵀ)ᵀ = (dL/dM_hat)QQᵀ` (Part III.7 eq, INF-9). There is NO `torch.autograd.Function`, NO `.detach()` on `M`, and NO straight-through shortcut (`M_hat = M + (proj(M)−M).detach()`) anywhere in the file. The backward is the genuine autograd of two matmuls with a constant right-multiplier.
- **Self-adjointness + idempotency when `QᵀQ=I`.** `init_basis` returns `orth(randn)` (QR ⇒ `QᵀQ=I`) and every update sets `Q=orth(V)` (QR again), so `P=QQᵀ` is symmetric (`P=Pᵀ`) and idempotent (`P²=P`); the *same* operator hits the activation (forward) and its gradient (backward) — this is INF-9's "gradient is biased, not just the activation."
- **Empirical (my own reproduction, fp32, H=8/r=3/N=5).** Autograd `dL/dM` vs analytic `(dL/dM_hat)QQᵀ`: `max abs diff = 0.0`. Finite-difference (eps=1e-3) vs autograd: `2.7e-4` (truncation-consistent). `P=Pᵀ`: `0.0`. `P²=P`: `4.8e-7`. Non-expansive `‖M_hat‖=3.83 ≤ ‖M‖=5.49`. The committed `test_autograd_no_ste` (asserts rel `<1e-5`) and `test_r_equals_H_lossless` (rel `<1e-4`) encode exactly this and the `r=H` identity continuity (INF-18).
- **On-box.** `q_cond≈1.0000003` on all 7 boundaries at both probe steps ⇒ `QᵀQ=I` holds in practice (fp32 QR not degrading orthogonality), so the projector algebra the backward rests on is real, not nominal.

## Check 2 — Gradient checkpointing: recompute sees identical frozen Q ⇒ identical M_hat ⇒ consistent gradient; sketch folds EXACTLY ONCE; old-logprob folds NOTHING — **VALID**

This is the subtlest check; I traced it to the torch source and reproduced it.

**(a) The hook fires TWICE on a gradient-bearing checkpointed forward, BOTH with grad enabled.** `gradient_checkpointing_enable(... use_reentrant=False)` is applied to the inner HF module (`transformer_impl.py:298`); each `GradientCheckpointingLayer.__call__` (transformers `modeling_layers.py:92`) routes through `self._gradient_checkpointing_func(partial(super().__call__,…), *args)` — i.e. the checkpoint wraps `nn.Module.__call__`, which is what *runs the registered forward hook*. So the hook fires **inside** the checkpoint region, on both passes:
  - *Original forward*: in `_checkpoint_without_reentrant_generator` (torch `utils/checkpoint.py:1643-1651`), when grad is enabled the region runs under `_checkpoint_hook` (a `saved_tensors_hooks` that swaps saved activations for `_Holder` placeholders) + `forward_context = nullcontext()` — grad is **NOT** disabled (the `if not torch.is_grad_enabled(): return` short-circuit at `:1643` is the *passthrough* branch, taken only when the *whole* outer forward is already no_grad). The autograd graph node for `M_hat` IS built here.
  - *Recompute*: triggered lazily by `unpack_hook` (`:1149-1170`) under `_recomputation_hook` **+ `torch.autograd.enable_grad()`** (`:1163-1165`), which re-invokes `recompute_fn`→`fn`→`super().__call__` ⇒ the hook fires again, also with grad enabled.

  I reproduced this with a real `torch.utils.checkpoint.checkpoint(blk, x, use_reentrant=False)`: the hook fired **twice** with `is_grad_enabled() == [True, True]`.

**(b) The `grad_enabled`-at-hook-entry flag does NOT distinguish original-vs-recompute — the `_fwd_generation` dedup does.** The code captures `grad_enabled = torch.is_grad_enabled()` at hook entry (`powersgd_activation.py:316`), before the `no_grad` diagnostics block. Under (a), this is `True` in BOTH the original forward and the recompute, so it cannot be what prevents double-folding V. What prevents it is `_should_accumulate_sketch`'s third gate (`:415`): `self._sketched_this_gen.get(layer_idx,-1) != self._fwd_generation`. `set_context` bumps `_fwd_generation` **once per micro-batch** in `prepare_model_inputs` (`transformer_impl.py:1751`), and the backward recompute does **not** re-enter `prepare_model_inputs`, so the recompute reuses the same generation ⇒ the layer's `_sketched_this_gen` already equals the current generation ⇒ the recompute's fold is skipped. V is built from the original forward only, exactly once per micro-batch. My reproduction confirmed: `V(ckpt, deduped) == V(no-ckpt)` to `0.0`, and `grad(ckpt) == grad(no-ckpt)` to `0.0`.

  > This refines (and corrects) the framing in the code comment at `:308-315` and in the superseded `math_validity_review.md` claim-1 companion: the comment's "reading is_grad_enabled() inside the no_grad block would always be False" is true *of the inner diagnostics block*, but it is **not** the recompute that grad_enabled excludes (the recompute is grad-enabled) — it is the *whole-forward-no_grad old-logprob pass* (Check 2c). For grad-ckpt dedup specifically, the generation counter is load-bearing, not grad_enabled. The committed `test_grad_ckpt_recompute_not_double_counted` exercises the dedup by re-running the forward in the same generation (a faithful proxy); my `torch.utils.checkpoint` reproduction exercises the *actual* recompute and confirms identical behaviour.

**(c) Recompute is bit-identical because Q is frozen for the whole step.** Q is written ONLY in `maybe_update_basis` (`powersgd_activation.py:512-513`), called from `engine_workers.py:943` in the `finally:` of `train_mini_batch` — i.e. AFTER the actor backward. The hook only *reads* `self._basis`. So during the original forward and its in-backward recompute, `_ensure_basis` returns the identical `Q_t` tensor; the recomputed `M_hat=(M'@Q_t)@Q_tᵀ` matches the value autograd saved/expects → consistent gradient, no "recompute differs from forward" hazard. (`check_recomputed_tensors_match`, torch `:1171`, would otherwise raise.) The committed `test_q_frozen_within_step_advances_only_on_update` pins that extra in-step forwards leave Q untouched and only `maybe_update_basis` advances it (to an orthonormal Q).

**(d) The old-logprob `forward_only=True` recompute folds NOTHING.** `compute_log_prob`→`infer_batch` runs `forward_step` under `ctx = torch.no_grad()` (`transformer_impl.py:864`). The whole forward is no_grad ⇒ at hook entry `grad_enabled=False` ⇒ `_should_accumulate_sketch` returns False at its first gate (`:409`). My reproduction of a no_grad forward: hook fired once, `is_grad_enabled()=[False]`, V unchanged. The recompute still *projects* (so `compress_recompute=true` shares the same Q_t for the IS-ratio denominator), but never sketches. Committed `test_old_logprob_recompute_projects_but_no_sketch` asserts exactly this (applications increase, `_sketch_count` unchanged).

**(e) On-box.** `powersgd_basis_updates` 1.0→2.0 over the 2-step probe (one orth(V) per step, post-backward); `reconstruction_rel_error` falls sharply on tracked layers (layer_3 0.97→0.025) ⇒ the warm-start power iteration is advancing a stable Q. *(Note: `powersgd_applications`≈3584/step = 512 fires × 7 boundaries reflects the double-fire of (a) plus per-PPO-microbatch count; this is a pure counter artifact — `note_powersgd_application` ticks on every hook fire including recompute — and has NO effect on V (deduped) or the gradient. Flagged as cosmetic, not a defect.)*

## Check 3 — Off-graph `with torch.no_grad(): V += …` cannot leak into the graph or perturb M_hat's grad — **VALID**

The diagnostics + sketch live in `with torch.no_grad():` (`powersgd_activation.py:343-382`), AFTER `M_hat` is formed (so they cannot alter the already-built graph node):
- `M32 = M.detach().float()`, `Mhat32 = M_hat.detach().float()` — explicit `.detach()`; norms touch no graph.
- `contrib = M32.t() @ Y.detach().to(torch.float32)` (`:374`) — `Y.detach()` severs the sketch from the graph; `V` is a side buffer keyed in `self._sketch`.
- `cur.add_(contrib)` (`:380`) is an in-place add on a **plain dict tensor**, NOT on `M`/`Y`/`M_hat`. No graph tensor that autograd will later need is mutated in place ⇒ no "variable modified by an inplace operation" hazard. The only graph-affecting output of the hook is `M_hat`.

Empirically (Check-1 reproduction): with the no_grad V-fold present, `M.grad` is bit-identical (`0.0` diff) to the analytic projector — the sketch is provably inert.

## Check 4 — FSDP interaction (`use_orig_params` / flat-param / `no_sync` / `summon_full_params` / all-gather / reduce-scatter) — **VALID**

- **Each decoder block is its own FSDP unit; the hook is on the FSDP-wrapped block.** FSDP1 is applied with a transformer-block `auto_wrap_policy` (`transformer_impl.py:362-398`). `find_decoder_layers` finds the `nn.ModuleList` named `layers` on `self.module` (the FSDP-wrapped top model), so `layers[idx]` is the FSDP-wrapped `Qwen2DecoderLayer` and `register_forward_hook` (`:663`) attaches to it.
- **A forward POST-hook fires after the unit's forward completes — downstream of all flat-param machinery.** By the time the post-hook runs, FSDP has all-gathered the block's sharded params, run the block compute, produced the hidden-state output, and (FSDP1) is about to reshard. The hook receives the materialized full activation `output[0]` and substitutes `M_hat`. This is a pure tensor swap on the block *output* — it never reads or writes a flat-param, a shard, or a `.grad`. So it cannot perturb `summon_full_params`, the flat-param contract, or the all-gather/reshard schedule.
- **`use_orig_params` is immaterial to this hook.** Unlike the anchor/spectral paths (which read `.grad` off named params and therefore *require* `use_orig_params=true`), the PowerSGD hook is parameter-agnostic: it transforms activations and accumulates an off-graph activation second-moment. `use_orig_params` true or false is irrelevant to its correctness. (The launcher still sets it true for the broader comm-eff machinery; confirmed in the probe config.)
- **In-graph M_hat is compatible with FSDP's backward collectives.** The projection inserts one extra linear node between the block output and the downstream consumer. Its backward `dL/dM=(dL/dM_hat)QQᵀ` flows the gradient into `M` (the block output), which then flows into the block's params exactly as in dense — FSDP's param all-gather (for grad recompute) and grad reduce-scatter operate on the block parameters and are agnostic to what transform sits between blocks. Q is a plain non-FSDP, non-parameter buffer on the compressor object ⇒ never sharded, all-gathered, or reduce-scattered.
- **`no_sync` (grad-accum across micro-batches) is irrelevant.** The hook does not call `.backward()`, reduce gradients, or depend on FSDP's deferred-reduction state; `V` is a plain Python-dict sum over micro-batches.
- **Same mechanism as the validated PRF masker.** `register`/`unregister`/`set_context`/output-tuple handling all mirror `ActivationMasker` (shared `find_decoder_layers`/`decoder_boundary_indices` ⇒ identical boundary placement, as the matched-budget comparison requires), and the masker has run under this exact FSDP config through prior EXPs.
- **On-box corroboration.** The 2-step probe ran with `use_orig_params=true` + grad-ckpt + the hook live on 7 boundaries, completed both steps, took an optimizer step, saved a checkpoint, `q_cond≈1`, with **no** `summon_full_params`/`flat_param`/NaN/OOM error in the log — direct evidence the output-replacing hook coexists with FSDP flat-param mechanics.

Guards (correct, asserted at registration): `_comm_eff_register_powersgd_hooks` refuses Ulysses SP>1 (`transformer_impl.py:776-781`) and `_comm_eff_maybe_set_powersgd_context` refuses non-rmpad/padded inputs (`:811-817`) — SP slices the token axis the projector compresses; padded forwards would fold PAD tokens into M and V. The launcher runs SP=1 + rmpad, so neither fires in the sanctioned config; they are the correctness boundary, not a defect.

## Adversarial cross-check of `math_validity_review.md` claim 1 (no-STE projector): **CONFIRMED**

The mathematical-checker's claim 1 ("Projector + autograd, no STE — VALID": Q detached, M in-graph, `dL/dM=(dL/dM_hat)QQᵀ`, idempotent when `QᵀQ=I`) is **confirmed at the mechanism level**, with one refinement.

- **Confirmed.** I independently traced the `.detach()`/`requires_grad` placement (Q never requires grad; M is a live view; `.to(dtype)` preserves non-requires-grad), confirmed there is no `autograd.Function` and no straight-through arithmetic anywhere in the forward, and reproduced the projector backward numerically (`max|autograd − (dL/dM_hat)QQᵀ| = 0.0`; finite-diff `2.7e-4`; `P=Pᵀ` and `P²=P` to fp32 tol; non-expansive). On-box `q_cond≈1` confirms `QᵀQ=I` is maintained, so the self-adjoint/idempotent algebra the backward relies on is real.
- **Refinement (not a contradiction).** The claim-1 *companion* discussion of the `grad_enabled` gate frames it as the thing that excludes the grad-ckpt recompute. That is imprecise: under `use_reentrant=False` the recompute is **grad-enabled** (I reproduced `[True, True]`), so the recompute is excluded from V-folding by the `_fwd_generation` **dedup**, while `grad_enabled` excludes the *old-logprob whole-forward-no_grad* pass. The end-state both reviews assert — V folds exactly once per micro-batch, gradient is consistent — is correct; only the attribution of *which* gate does *which* job needed sharpening (Check 2b above).

**What would refute my conclusion.** (1) If `Q` were ever an `nn.Parameter` / `requires_grad=True` / registered buffer the optimizer touched, the backward would no longer be the pure projector and a `dM_hat/dQ` edge would exist — I checked: it is a plain dict tensor from detached/QR sources. (2) If `set_context` were moved to fire on every forward invocation (incl. recompute), the `_fwd_generation` dedup would break and V would double-count — today it fires once per micro-batch in `prepare_model_inputs` and the recompute does not re-enter it (a real forward-fragility, flagged below). (3) If a future `use_reentrant=True` switch were made, the recompute would run inside a nested autograd graph under its own `torch.enable_grad`, and the saved-tensor/holder mechanism differs — the dedup-by-generation would still hold (set_context still fires once), but this path is untested here; the committed config pins `use_reentrant=False`. (4) If grad-ckpt were ever applied to a wrap unit that does NOT re-run the registered module's `__call__` on recompute (e.g. a functional/custom checkpoint that bypasses `nn.Module.__call__`), the hook would not re-fire and the recompute would use a stale/absent M_hat — not the case for HF `GradientCheckpointingLayer`, which routes through `super().__call__`.

## Bottom line (Task #2)

**The autograd and gradient-checkpointing mechanics are correct — all four checks VALID, math claim 1 CONFIRMED.** Q is a detached constant, M stays in-graph, and the backward torch computes is the genuine self-adjoint projector `dL/dM=(dL/dM_hat)QQᵀ` with **no** straight-through estimator and **no** custom autograd Function (verified at the op level and numerically, `0.0` diff). The off-graph `no_grad` diagnostics/sketch (explicit `.detach()` on M and Y, in-place add only on a side dict buffer) provably cannot perturb the gradient. Under non-reentrant gradient checkpointing the hook re-fires on the in-backward recompute **with grad enabled**, and the recompute sees the **identical frozen Q_t** (the basis advances only post-backward in `maybe_update_basis`), so the recomputed `M_hat` is bit-identical and the gradient is consistent; the per-`_fwd_generation` dedup — not the `grad_enabled` flag — is what folds V exactly once per micro-batch, while the `grad_enabled`-at-hook-entry capture is what excludes the whole-forward-no_grad old-logprob recompute (reproduced: `[True,True]` for ckpt, `[False]` for forward_only). The output-replacing `register_forward_hook` fires after each FSDP-wrapped decoder block completes — downstream of all flat-param / all-gather / reshard / `summon_full_params` machinery — and never reads params or grads, so `use_orig_params` / flat-param / `no_sync` are immaterial; the on-box probe (use_orig_params=true + grad-ckpt + hook live, `q_cond≈1`, no NaN/OOM/FSDP error, basis_updates 1→2) confirms coexistence.

**No defects.** Forward-fragility notes (not current bugs): (1) the grad-ckpt V-dedup relies on `set_context` firing once per micro-batch and NOT being re-called on recompute — robust at `f748dbc` but would break if a refactor moved the generation bump into the per-forward path; (2) the `use_reentrant=False` assumption is load-bearing for the recompute-re-fires-the-hook reasoning — a switch to `use_reentrant=True` should be re-reviewed; (3) cosmetic: `powersgd_applications` double-counts the grad-ckpt recompute fire (no effect on V or gradients). The SP=1 / rmpad guards are the hook's correctness boundary and are asserted at registration.
