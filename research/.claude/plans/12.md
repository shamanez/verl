> **REVISE root cause (decided by EXP-8 analyst verdict, 2026-05-28).** Cells 1
> (faithful) and 3 (lean) of EXP-8 crashed identically at step 0:
> `_maybe_comm_eff_anchor_refresh → _forward_backward_batch_inner:717 loss.backward()
>  → torch FSDP _post_backward_hook → _check_grad_to_accumulate(... flat_param._saved_grad_shard)
>  → AttributeError: 'NoneType' object has no attribute 'shape'`. The anchor's
> `loss.backward()` ran on the FSDP1-wrapped live actor module and triggered
> the fast-path's `_post_backward_hook`, which read `flat_param._saved_grad_shard`
> outside its backward window (where it is `None`). Cell 2 (`anchor.enabled=false`)
> completed `global_step:5` cleanly with `mask_applications=70`,
> `spectral_corrections=40`, all `anchor_*=0`, finite `actor/grad_norm` — proving
> the mask + spectral stack is sound and the regression is wholly isolated to
> the anchor backward. Lean storage knobs (cpu/lowrank/seed=false) did NOT
> mitigate it. **The fix is to break the autograd-hook chain — run the anchor
> on a module that is NOT registered with FSDP, OR wrap the anchor in
> `FSDP.no_sync() + summon_full_params()` with `_post_backward_hooks` suppressed.**

## next_actions (verbatim from `runs/EXP-8/verdict.md`)

```yaml
- knob: anchor_backward_graph_isolation
  from: live_fsdp_module
  to: cloned_no_hook_module
  rationale: |
    The anchor `loss.backward()` at engine/fsdp/transformer_impl.py:717 is
    invoked from `_maybe_comm_eff_anchor_refresh` (line 869) on the actor's
    FSDP1-wrapped module. That backward fires FSDP1's
    `_post_backward_hook -> _reduce_grad -> _accumulate_sharded_grad`, which
    reads `flat_param._saved_grad_shard.shape` — but `_saved_grad_shard` is
    `None` outside the fast-path's backward window, so it raises
    `AttributeError: 'NoneType' object has no attribute 'shape'`.
    Break the autograd-hook chain by running the anchor on a deep-cloned
    module whose parameters are detached from the FSDP registration (clone
    params off the optimizer group, off the FSDP `_handles`), OR wrap the
    anchor fwd/bwd inside `FSDP.no_sync()` + `summon_full_params()` with
    `_post_backward_hooks` explicitly suppressed for the duration of the
    anchor pass. Either path satisfies the parent plan's Note "the anchor
    snapshot can be a cheap CPU/GPU clone of the actor params at step
    t-delay_K" and the load-bearing guard "snapshot OFF the optimizer's
    parameter group" (a cloned no-hook module is by construction off the
    FSDP fast-path graph).
- knob: anchor_optimizer_param_group
  from: shared
  to: disjoint
  rationale: |
    Defensive belt-and-braces with the cloned-module change: ensure the
    snapshot parameters do not appear in the live optimizer's
    `param_groups`, and are not registered with the FSDP `_handles` /
    `_root_pre_forward_handles`. Independently required by criterion 7
    (`anchor_optimizer_steps == 0`, snapshot off the optimizer's parameter
    group — load-bearing per the plan's `## Notes for runner`). Verifying
    disjoint-param-group post-clone is cheap and prevents a class of
    regressions if the cloned module accidentally shares storage with a
    live FSDP-handled `FlatParameter`.
```

## Background pointers

Inherits all of `.claude/plans/8.md §Background pointers` verbatim. Additionally:

- **FSDP1 autograd-hook chain (the load-bearing source for this REVISE).** When
  the fast-path enters `train_batch`, FSDP1 registers
  `_post_backward_hook` on each `FlatParameter`'s post-accumulate-grad hook
  (per `torch.distributed.fsdp/_runtime_utils.py`). That hook calls
  `_reduce_grad`, which calls `_accumulate_sharded_grad`, which calls
  `_check_grad_to_accumulate(sharded_grad, flat_param._saved_grad_shard)`.
  `_saved_grad_shard` is set up by the fast-path's pre-backward and torn down
  after the optimizer step. The anchor's backward fires the SAME hook because
  the cloned-but-still-FSDP-wrapped params are part of the same graph — they
  reach `_check_grad_to_accumulate` against a `None` `_saved_grad_shard`.
  The fix: the anchor pass must NOT trigger FSDP1's post-backward hook.

- **Cell 2 result is the EXP-7 reproduction control** (kept as a regression
  cell in this REVISE — see §Experiment design below). It already passes; we
  carry it forward to confirm the fix does not regress the anchor-off path.

## Debug workflow (this lineage only — anchor-circuit defect investigation)

EXP-8 proved that the defect (`_check_grad_to_accumulate` `AttributeError`
on `flat_param._saved_grad_shard`, raised from
`_maybe_comm_eff_anchor_refresh → loss.backward()`) surfaces **only under
production FSDP1 runtime**: all 54 CPU unit tests passed clean, then two of
three cells crashed at step 0 on the box. **CPU testing is necessary-but-
not-sufficient on this lineage; debugging MUST happen on a Vast.ai box.**
The plan therefore treats Vast.ai as the primary development surface for
the duration of the EXP-8 → EXP-12 → ... lineage, not as a single-shot
validation target reached at the end of a CPU-test-and-push cycle.

### First provisioning attempt: consumer card, single shot

The `gpu_filter_chain` (above) lists consumer Ada/Blackwell first. The
runner provisions the **first available consumer tier** (`8×/4× RTX_5090`,
then `8×/4× RTX_4090`) and launches the 3-cell smoke. **ONE consumer
attempt only.** If the consumer instance fails the environment / setup
gate — defined in the triage table below — the runner MUST:

1. Tear down the consumer instance immediately (no retries on a different
   consumer host — env mismatches don't get more tractable by re-rolling
   a 4090).
2. Re-provision from the H100/H200 portion of the chain (skip the four
   `RTX_*` entries; start at `4× H100`, walk to `H200` / `8×` as the
   chain dictates).
3. Continue the lineage's debug iteration on the larger card.
4. Record BOTH the consumer-tier and the H100/H200-tier rows in
   `runs.jsonl` — the consumer one with
   `teardown_reason: "env-failure: <ctx>"` (specific: docker-fail / cuda-
   driver-mismatch / vllm-init-OOM / nccl-init-fail / ssh-unreachable) so
   the orchestrator can audit the fallback rate later.

The single-shot-then-fallback rule exists because the *purpose* of trying
the consumer card first is to make ITERATION cheap — not to gamble on
flaky 4090 hosts. If we can't even start training on a consumer host, we
stop paying that ~3-5× pricing premium for a problem we have no leverage
to solve on the cheap card.

### What is "env failure" (fall back NOW) vs "experiment failure" (KEEP running, analyst grades)

| Symptom on the box                                                                | Treatment |
|---|---|
| Docker container fails to start (image pull / CUDA driver mismatch)               | **env-failure** → tear down → H100/H200 |
| Bundled torch (`2.11.0+cu130`) refuses to import (host CUDA < 13.0)               | **env-failure** → tear down → H100/H200 |
| vLLM init OOM **before** training begins, even with `gpu_memory_utilization=0.5`  | **env-failure** → tear down → H100/H200 |
| NCCL init / P2P fails on the consumer tier                                        | **env-failure** → tear down → H100/H200 |
| Persistent SSH unreachability >2 min after `vast-provision` declares routable      | **env-failure** → tear down → H100/H200 |
| First cell's `validate_config` passes, model loads, vLLM rollout engine ready, training starts, then anchor fwd/bwd raises `AttributeError` / NaN / OOM | **experiment failure** — keep cells 2+3 running; this is the data we're paying for; let analyst grade per the predicate |
| `comm_eff/anchor_*` counters wrong values mid-training (`anchor_mask_applications > 0`, `anchor_grad_corrected > 0`, etc.) | **experiment failure** → analyst REVISE |
| `actor/grad_norm` non-finite mid-training                                          | **experiment failure** (route to `codex-bridge --mode=code-rescue` if a rescue-trigger regex fires) |

### In-place iteration on a RUNNING box (operator's prerogative)

Once an instance is RUNNING and producing training data, the operator MAY
iterate the fix **directly on the box** without tearing down between
attempts. This is the load-bearing reason for "everything on Vast" — the
FSDP1 collision is only reproducible there, so iteration cycle time is
dominated by box wall-clock, not provisioning latency.

Pattern (operator-driven, NOT runner-driven):
1. SSH in via the handle's `ssh_login` string (in `runs/EXP-12/handles/<id>.json`).
2. `cd /workspace/verl`; apply a hot-fix in place on `exp/12-anchor-detach`.
3. Capture the diff: `git diff > /workspace/runs/EXP-12/iterations/<N>.patch`
   (commit it to the branch when you SSH-out so the local laptop also has it).
4. `tmux kill-session -t exp-12-<host>`; relaunch the 3-cell chain with the
   hot-fix applied. Per-cell `EXPERIMENT_NAME` should also get the iteration
   suffix (`m2-anchor-faithful-iter<N>`) so WandB doesn't auto-resume the
   prior crashed run (EXP-6 caveat).
5. Watch logs + GPU util + WandB per `memory/active-vast-monitor.md`
   (30 s cadence, never trust `done_<cell>.flag` alone).
6. Repeat until either: (a) all three cells PASS the plan's predicate, or
   (b) the lineage exhausts `iterations: 3`, or (c) `max_gpu_hr=10`
   exhausts.

The runner's contract remains "provision → launch first cells → register
RUNNING → stop". `runs.jsonl` row stays RUNNING across in-place iterations;
the analyst is dispatched only when the operator decides the cycle is
decisively terminated (verdict.md is then evaluated against the accumulated
evidence in `runs/EXP-12/iterations/`).

If the operator does NOT iterate in place (i.e., wants a clean run per
fix), then the standard cycle is: teardown → next plan revision → next
runner dispatch → next provisioning. Either path is valid; the in-place
path is the cost-optimal one when the FSDP defect surfaces fast (within
seconds of training start, as it did in EXP-8).
