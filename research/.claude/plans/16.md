> (plus a GPU pre-flight gate) on a single warm Vast.ai box, on a single
> experiment branch `exp/16-short-run-stability-matrix`, executed and monitored
> by a **Claude Code agent team** (lead + 4 named teammates). The science
> question: at the unstable high-mask point (`p=0.9`), which stabilizer —

## Hypothesis

Within the first 10–25 trainer steps, at least one communication-efficient
configuration (mask+rescale, mask+clean-cadence, or mask+rescale+spectral+anchor)
can stay **numerically stable** — finite `grad_norm` throughout, **zero** NaN/Inf
in any loss/grad/reward field, no FSDP backward/hook error, no DTensor↔Tensor
writeback error — AND move **measurably closer to the dense GRPO learning
trajectory** than the current unstable high-mask control (mask-only, no-rescale,
`p=0.9`). Falsifiable thresholds (a PASS requires ALL): (a) the dense reference
cell 6 itself stays finite and shows a non-negative `train/reward_mean` /
`val/test_score` trend over its 25 steps (the screen's own sanity anchor); (b) at
least one comm-eff cell reaches its full `TOTAL_TRAINING_STEPS` with `grad_norm`
finite at every logged step and **max `grad_norm` within 10×** the dense cell's
max `grad_norm` (same order of magnitude); (c) that cell's GRPO clipping is
**not saturated** — `actor/pg_clipfrac` does not climb monotonically toward 1.0
and `actor/pg_clipfrac_lower` is not pinned (a non-saturated, non-degenerate
clipping signature); (d) that cell's step-20/25 `train/reward_mean` (or
`val/test_score` where logged) is **strictly greater** than the mask-only
no-rescale control's value at the same step. If NO comm-eff cell clears (b)+(c)+(d),
the high-mask method is judged not-yet-stabilizable by these knobs at `p=0.9` on
this screen and the verdict is STOP/REVISE per `## Analyst predicate`. These are
operational stability + relative-trajectory thresholds appropriate to a short
diagnostic screen — they do not assert dense parity (that is the later 25-step
follow-up's job under `## Follow-up gate`).

### Handoff points
1. **runner → lead (plan-mode gate):** the runner is spawned in plan-approval
   mode; it drafts the spectral-cadence + delay_K code change (task T5) and
   the cell-0 GPU test as a plan, and stays read-only until the lead approves.
   This satisfies "require plan approval before teammates make code changes."
2. **runner → wandb-monitor / auditor (per cell):** when a cell's training
   launches, the runner messages the monitor (and, for cell 5, the auditor) the
   WandB run name + on-box `train.log` path so they can attach immediately.
3. **wandb-monitor / auditor → lead (kill-switch):** on any kill-switch-class
   signal (`## Monitoring + kill-switch lane`), the monitor/auditor messages the
   lead + runner; the runner stops the cell early; the lead records it.
4. **all → verdict-synthesizer (end):** once T7 + A5 + all M* are completed, the
   synthesizer builds the table and the verdict.
5. **lead cleanup (end):** the lead shuts down each teammate, then cleans up.

## Execution discipline (the issue's hard requirement)

- **Sequential ONLY.** `max_parallel: 1`. Never launch two Vast.ai training jobs
  for this matrix at once. Complete → inspect → record each cell before the next.
  Rationale (from the issue): unstable FSDP/spectral failures need immediate
  diagnosis, and parallel failures make logs uninterpretable and waste compute.
- **ONE branch for everything:** `exp/16-short-run-stability-matrix`, cut from
  `origin/vast-ai-workload`. ALL code changes (T5 spectral cadence + delay_K +
  numeric metrics + early-stop) and ALL runs live on it. **No per-cell, per-bug,
  or per-launcher-fix branches.** Fixes are applied + validated on this branch
  before the next cell; the runner records what changed (commit + a line in the
  resolved-config artifact + the verdict).
- **Code changes during testing are explicitly allowed** but must be **narrowly
  scoped** to making this matrix runnable + interpretable, must **preserve the
  fixed controls**, and must be a **strict no-op when `COMM_EFF_ENABLED=false`**
  (cell 6 is the proof). If a fix changes method semantics, the runner documents
  the reason in the issue comments + the resolved-config artifact + the verdict,
  and proves the dense reference (cell 6) still runs cleanly.
