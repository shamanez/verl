## Hypothesis

A config-gated post-`_save_checkpoint` R2 upload hook (built on the existing `R2ArtifactSink`) can mirror every `global_step_<N>/` checkpoint tree to R2 **on-the-go** — uploading each file as soon as it is written and deleting the local copy after its upload verifies — such that, over a **1000-step** vanilla-GRPO run of Qwen2.5-1.5B-Instruct on Big-Math-RL-Verified-filtered at `MAX_RESPONSE_LENGTH=4096`, the following hold (all machine-checkable, artifact-completeness-shaped — this is a collection run, not a reward-threshold run):
1. **Method-OFF byte-parity:** with the gate unset (`CKPT_R2_ENABLED` absent), `_save_checkpoint` is byte-identical to upstream verl — no R2 threads spawned, no new imports on the save path.
2. **On-the-go / disk-bounded:** with the gate ON, checkpoint objects appear in R2 *during* training and each local file is deleted after a verified upload, so peak local disk stays bounded (≈ 1 in-flight checkpoint ~22 GB + staging ≤ `CKPT_R2_MAX_STAGED_GB`), NOT the keep-all ~1100 GB total.
3. **Resume completeness:** the R2 mirror is resume-valid — the root `latest_checkpointed_iteration.txt` is re-uploaded each save and all sharded files (`model_/optim_/extra_state_world_size_<W>_rank_<R>.pt` × world_size, plus `data.pt`) are present, so `find_latest_ckpt_path` can resolve the latest step from R2 alone (a dry restore test confirms it).
4. **Artifact set:** the `weights/` R2 manifest shows **50** `verified:true` fp32 snapshots (steps 20,40,…,1000; `dump_dtype=fp32`) and the `checkpoints/` R2 manifest shows a complete `verified:true` object set for each of the same 50 steps.

Falsified if any `hard` correctness invariant fails and cannot be fixed on the `exp/` branch, or if the run cannot reach 1000 steps at resp=4096 on any rung of the GPU ladder.
