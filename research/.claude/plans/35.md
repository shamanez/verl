## Hypothesis

On the locked B2 substrate (PowerSGD r=77 + mandatory anchor owning Q,
cadence=delay_K=5, paired replay, clean_cadence=0), with the `signed_ema`
merger at the EXP-34 peak `beta_anc=0.50`, sweeping the merger weight
`signed_ema_alpha ∈ {0.0, 0.25, 0.5, 0.75, 1.0}` traces a non-degenerate α ridge
whose interior peak is at, above, or below 0.5. **Falsifiable predictions:**
(1) **Surface-validation GATE** — the α=0.5 cell (C3) reproduces the
locked-surface SOTA **val@50 = 0.7635 within ±0.024** even under the accelerated
4×H100 control surface (dynamic batching + TP=1 + max_response 2048); if C3
falls outside that band, dynamic batching perturbed the anchor/merger and the
absolute numbers are void (relative ranking may still hold). (2) **Curve
endpoints** — α=1.0 collapses to the no-merger PowerSGD floor (val@50 ≈ 0.63,
expect ≤ 0.66) and α=0.0 is the degenerate sign-SGD regime (entropy-collapse /
length-ignition risk). (3) **Acceleration** — every cell finishes ≤ ~45 min/50
steps (stretch 30 min) with sustained per-GPU nvidia-smi util ≥ 90% near TDP
during `update_actor`, and `perf/max_memory_reserved_gb` driven high but staying
< ~76 GB on anchor-firing steps. (4) **One-knob** — all 5 cells differ ONLY in
`signed_ema_alpha`; the acceleration stack is byte-identical across cells. Per
the σ(M)-ceiling thesis α is a deterministic reweighting of (G, M), so it is
expected to stay in the dense parity band, NOT surpass dense — this sweep is
internally valid (best α among 5, self-validated by C3) but its ABSOLUTE numbers
are NOT comparable to the locked-surface ledger until dense + B2 are re-baselined
on the accelerated surface.

### Vast.ai utilization discipline (HARD RULE)

- **One instance for the whole sequence.** The step-0 probe + all 5 cells chain
  back-to-back on the SAME provisioned box (shared docker / verl checkout /
  dataset cache). No teardown/reprovision between cells.
- **Cells run sequentially** (each cell uses all 4 GPUs for the chosen
  footprint), not concurrently — `max_parallel=1`. They are `parallel_with`
  each other only in the sense of having no data dependency; the physical box
  runs them one after another.
- **GPU-saturation is a success criterion, not just hygiene.** The whole point
  of the acceleration stack is to drive the GPUs compute-bound. The monitor must
  confirm sustained util ≥ 90% near TDP during `update_actor`; sustained idle is
  a stall, not a designed gap.
- **Tear down the instant the last cell's val@50 is captured + rsynced.** No
  keep-warm. State lives in `runs/EXP-35/` on the laptop.
- **No legitimately-idle phase is designed in** — the monitor's default
  stall thresholds apply unchanged (the only short low-util windows are the
  inter-cell vLLM re-init gaps, which are brief and expected).

  default). EXP-34's verdict confirms `signed_ema_alpha` appears in
  `resolved_params.txt` only as the explicit override.
- **Acceleration stack via env (Tier 1) + Hydra (Tier 2).** Tier-1 dynamic
  batching is env-exposed on the generic launcher:
  `USE_DYNAMIC_BSZ=True`, `PPO_MAX_TOKEN_LEN_PER_GPU=<calibrated>`,
  `LOG_PROB_MAX_TOKEN_LEN_PER_GPU=32768`,
  `REF_LOG_PROB_MAX_TOKEN_LEN_PER_GPU=32768`, `MAX_RESPONSE_LENGTH=2048`. Tier-2
  (`tensor_model_parallel_size=1`, `gpu_memory_utilization=0.55`) is Hydra
  passthrough (not env-exposed). **Keep `PPO_MINI_BATCH_SIZE=64`** so 2 optimizer
  ticks/step are preserved ⇒ the anchor `cadence=5`/`delay_K=5` timing (counted in
  ticks, see memory `anchor-cadence-delayk-unit-optimizer-ticks`) is unchanged.
  **Keep `TRAIN_BATCH_SIZE=128`** (raising it does not speed a fixed-50-step run
  and would forfeit the C3 surface anchor — flip only on explicit operator
  decision; see Open decisions in the issue).
- **Step-0 memory calibration is the FIRST thing on the box.** Run a short probe
  (≥ 6 optimizer ticks = ≥ 1 anchor fire at cadence=5; the anchor's extra
  uncompressed backward is the memory peak, every 5 ticks). Start
  `PPO_MAX_TOKEN_LEN_PER_GPU=24576` and raise/lower until an anchor-firing step's
  `perf/max_memory_reserved_gb` ≈ 70 GB (∈ [68,76]; 4-8 GB OOM margin on 80 GB).
  Use that ONE value for all 5 cells. The goal is **compute-bound, not full
  VRAM** — optimize sustained util/power, not GB for its own sake; a 1.5B model
  saturates compute at a moderate budget. If 24576 OOMs on the probe, step down
  (16384 → 12288 → 8192). The probe runs on the sweep box; its val is NOT a
  deliverable.
- **Standing OOM guards (every cell regardless):**
  `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, `spectral.ema_device=cpu`
  (~6 GB fp32 M/EF state off-GPU — the wrapper sets it). On 4×H100 (80 GB) these
  are load-bearing; the 2048 response cap is what makes a large token budget safe.
- **vLLM box-compat break-glass.** `DISABLE_CUSTOM_ALL_REDUCE=true` is the
  wrapper default (NCCL all-reduce; greedy-val-neutral; required to dodge the
  `custom_all_reduce.cuh:455 'invalid argument'` CUDA-IPC crash at KV-cache init
  — see memory `vast-vllm-custom-allreduce-ipc-failure` + EXP-34 launch.sh, which
  hit it on attempt 1). Leave it at the default unless the specific box does not
  hit the crash. **With TP=1 there are 4 independent vLLM replicas and NO
  per-token all-reduce in generation**, so this flag's footprint shrinks anyway,
  but keep it set.
- **Team account.** `VAST_ACCOUNT=team` on provisioning AND teardown (handle
  stamps `vast_account=team`; both teardown paths read it back — see memory
  `vast-team-account-selector`). Team accounts can't hold account SSH keys ⇒ the
  provision skill does a per-instance `vastai attach ssh`.
- **`set -uo pipefail`, NOT `-e`.** A crashed/early-killed cell (e.g. a low-α
  ignition) must NOT abort the remaining cells — each cell is an independent draw
  and a failure IS data (mirror EXP-34's `launch.sh` `run_cell` pattern: per-cell
  rc captured + logged + continue; copy ONLY `train.log` + `done.flag` +
  `EARLY_STOP_SIGNAL` back to `runs/EXP-35/<cell>/`, never checkpoints/wandb
  blobs).
- **Heartbeat / teardown.** The `runs/EXP-35/metrics/incoming.log` MTIME drives
  the no-heartbeat teardown; the run-dir id must own it (see memory
  `extension-rows-heartbeat-contract`). Tear down the instant the last cell's
  val@50 is rsynced — don't trust the heartbeat backstop (sync keeps the MTIME
  fresh even when training is dead; memory `heartbeat-teardown-defeated-by-monitors`).
- **Likely first-launch failure surfaces** (start debugging here): OOM on an
  anchor-firing step at too-aggressive a token budget (→ the step-0 probe is the
  guard); the vLLM CUDA-IPC crash (→ DISABLE_CUSTOM_ALL_REDUCE=true default); a
  cell silently inheriting the wrapper's `delayed_ef` because a Hydra override was
  dropped (→ assert `correction_mode=signed_ema` in `resolved_params.txt` before
  trusting any val). None require a code edit; all are config/launch.

## Notes for analyst

- **The surface-validation GATE (C3 ∈ [0.7395, 0.7875]) decides
  interpretability.** Check it FIRST. If C3 passes, the absolute α curve is
  comparable to the locked-surface 0.7635 anchor. If C3 fails, do NOT compare
  absolutes to the ledger — report the α curve as relative-only and flag
  `C3-surface-FAIL` (next_action: re-test C3 with `USE_DYNAMIC_BSZ=False` to
  isolate dynamic batching).
- **Recalibrated ignition gate for the 2048 cap.** The locked-surface ignition
  gate watched `len/max > 4k` (on a 16384 cap). With `MAX_RESPONSE_LENGTH=2048`
  the cap is 8× smaller — recalibrate the early-gate to **`response_length/max >
  ~1.5k`** (i.e. > ~0.7 of the 2048 cap) and watch the standard collapse
  signatures (P1 consecutive clip-cap pins, P2 length-mean upward slope, P3 mean
  > 2× baseline). Low-α cells C1 (α=0.0) and C2 (α=0.25) are the ignition
  candidates (sign-SGD-ward). An early-kill IS data — record the kill step + last
  val; it is NOT a failed cell.
- **Per the σ(M)-ceiling thesis, expect parity, not surpass.** α is a
  deterministic reweighting of (G, M), so the whole curve should sit in the dense
  parity band (~0.75–0.78 on the LOCKED surface; the accelerated-surface band is
  unknown until re-baselined). A finding that the interior peak ≈ B2/dense parity
  is the EXPECTED, PASS-worthy outcome for this hypothesis — do NOT read parity
  as a STOP-grade falsification.
- **GPU saturation is a headline success criterion, not a footnote.** Weight the
  monitor's per-GPU util/power readings during `update_actor` as heavily as the
  val numbers — the dual purpose of this sweep is validating the acceleration
  stack. Confirm sustained util ≥ 90% near TDP and `max_memory_reserved_gb`
  driven high (< 76 GB) on anchor-firing steps. Report the `timing_s/*` breakdown
  so the `update_actor` + `old_log_prob` reduction (the ~87% slice) is visible.
- **val@50 is the headline; val@55 (if any cell runs total=55) is informational
  only** — but this plan pins `TOTAL_TRAINING_STEPS=50`, so the last step
  coincides with the test_freq val ⇒ val @ 25, 50 ONLY (no spurious val@55; see
  memory `no-end-of-training-val55`).
