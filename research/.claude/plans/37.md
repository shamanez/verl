## Hypothesis

On the locked accelerated comm-eff base (signed_ema alpha=0.25, beta_anc=0.50; PowerSGD r=77 anchor substrate; paired replay), increasing anchor latency from cadence/delay 5/5 to **20/20 optimizer ticks** (= 10 global-step staleness) and extending the run to **100 trainer steps** keeps signed_ema near the EXP-36B accelerated base rather than degrading materially or going unstable. Falsifiable thresholds: (1) the run completes 100 steps with **no NaN/Inf** in any loss field and **no length-ignition / entropy-collapse / persistent cold-M fallback** through steps 50-100; (2) `val@50 >= 0.6862` — i.e. within **0.05 absolute** of the EXP-36B accel base 0.7362 at the matched step (a degradation worse than 0.05 falsifies "remains near base"); (3) the staleness machinery realizes the intended latency: `anchor_backwards == 10`, `anchor_q_updates == 10`, `anchor_q_broadcasts == 10`, and realized data/weight delay `>= 20` ticks after warmup. This is a single realism draw, not a method-design or surpass-dense claim; the verdict is "interpretable + characterized", not "beats dense".

## Notes for runner

**CRITICAL launch gotcha — the issue body's env-var invocation will silently run the WRONG cadence/delay.** The accel base (`examples/grpo_trainer/vast_comm_eff_accel_base_qwen25_1p5b_grpo_gsm8k.sh`) does a **bare** `export COMM_EFF_ANCHOR_CADENCE=5` / `export COMM_EFF_ANCHOR_DELAY_K=5` (lines 21-22) with NO `${VAR:-...}` indirection. That bare export **overwrites whatever the caller put in the environment** before it exec's the generic launcher. So `COMM_EFF_ANCHOR_CADENCE=20 ... bash <accel base>` (the form written in the issue body) is clobbered back to 5 — the run would execute at cadence/delay 5/5 and be completely uninterpretable for this hypothesis.

**Use trailing Hydra args instead** (these come LAST and win under Hydra last-wins — the accel base forwards `"$@"` to the generic launcher, which ends its python invocation with `"$@"` at line 503, after the `anchor.cadence`/`anchor.delay_K` lines at 450-451):

```bash
PROJECT_NAME=verl_compression_research_accel_rebaseline \
EXPERIMENT_NAME=exp-37-cad20-delay20 \
TOTAL_TRAINING_STEPS=100 \
TEST_FREQ=25 \
  bash examples/grpo_trainer/vast_comm_eff_accel_base_qwen25_1p5b_grpo_gsm8k.sh \
    actor_rollout_ref.actor.comm_eff.anchor.cadence=20 \
    actor_rollout_ref.actor.comm_eff.anchor.delay_K=20
```

`PROJECT_NAME`, `EXPERIMENT_NAME`, `TOTAL_TRAINING_STEPS`, `TEST_FREQ` ARE properly `${VAR:-default}` (generic launcher lines 203-204, 53-54) and flow correctly via env — only the two anchor-latency knobs need the Hydra-arg path. Do NOT hand-edit the launcher (it is the locked EXP-36B reproduction surface, and the protect-upstream hook blocks edits off `exp/*`/`vast-ai-workload` anyway).

**Verify the override took before trusting the run**: the generic launcher echoes the resolved config; confirm the banner prints `anchor: ... cadence=20 delay_K=20` (line 352 format), and that `resolved_params.txt` / train.log show `anchor.cadence=20` and `anchor.delay_K=20`. If you see 5, abort and re-launch with the Hydra-arg form.

**WandB project**: must be `verl_compression_research_accel_rebaseline` (NOT the launcher default `verl_compression_research`) so the curves overlay EXP-36B (`rsvo7y1p`) and EXP-36C directly.

**Expected cadence math**: ppo_mini=64, train_batch=128 => 1 global step = 2 optimizer ticks => 100 trainer steps = 200 ticks. cadence=20 => **10 anchor fires**. The staleness ring retains delay_K+1 = 21 CPU snapshots (bounded; fine at 100 steps). Paired replay should show data_delay=20 and realized weight delay >= 20 after warmup, while replaying the exact rollout batch from the stale snapshot.

**Do NOT reintroduce the dropped vLLM speed knobs** (gpu_mem 0.75 / chunked_prefill / forward_prefetch — see `research/runs/SUMMARY.md`). Keep gpu_mem_util=0.55. Standing OOM guards are already in the launcher (`expandable_segments`, ema_device=cpu, snapshot_device=cpu, actor 24576).
